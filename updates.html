For existing ships · not a fresh build

Manual updates

Already built a ship from the starter prompt? These are standalone, paste-able upgrade prompts — apply just the ones you want, in any order, without rerunning the full interview. Each one figures out your ship's actual file names and mythos on its own.

Series: v2 architecture

6 updates

Core-architecture patterns folded into the v2 starter prompt: spine index/detail splitting, external task-board sync, entity spine files, a standing status index, two-tier context awareness, and an automation-mechanism guardrail. None depend on each other.

paste this prompt 
Your ship's boot sequence currently reads the full orchestration/dispatch log and the full open-questions register at every session open. I want to split both into a lightweight index + full detail file, so boot stays cheap as they grow.

1. Find your ship's dispatch/orchestration log (tracks work handed to crew members) and your open-questions/parked-questions register. They're probably under a spine/memory directory — find them by content, not by an assumed filename.

2. For the dispatch log: create a new file that's a **boot-read index** — one line per *currently open* dispatch (status icon, who it's assigned to, what the task is, when it opened). The existing full log stays as-is and keeps every entry, including closed ones — that remains the permanent record.

3. For the open-questions register: create a new file that's a **boot-read index** — one line per question (ID, the question itself, current status). The existing full register stays as-is with full detail per entry.

4. Update your boot sequence (wherever it's defined — your main instruction file and/or your ship's spec file) to read the two new index files at boot instead of the two full files. State explicitly that the full files are only pulled when actively working that specific thread, not at every boot.

5. Update whichever role writes to these logs (your router/orchestrator role) so it writes to *both* files going forward: full detail to the log, one-line summary to the index. When a dispatch closes, remove it from the open index but keep it in the full log.

6. Backfill the two new index files from whatever's currently open in the existing full files, so this doesn't lose any live state.

I want you to evaluate whether my ship's memory/spine should stay file-based or move to a cloud memory API, and document the decision either way so it doesn't get re-litigated later.

1. Identify what my current memory setup actually is — plain markdown/text files on disk, a cloud memory API, a database, or some mix.

2. Reason through the tradeoff explicitly: files read at every session open benefit from being local (no network latency, no API cost per read, works offline, trivially diffable/greppable). A cloud memory store adds cost and latency to something that happens dozens of times a week, and most cloud memory products are optimized for semantic search over large corpora, not for "read the same five files every single time."

3. If I already have a sync/backup mechanism for my files (a synced drive folder, git, etc.), note that this already solves the durability problem a cloud store would solve — so the cloud store isn't buying me anything my current setup doesn't already have.

4. Write your recommendation into a short decision note in my spine (a lessons log if I have one — see Update 5 — otherwise a new short file). State the decision and the reasoning in 3-4 sentences so future-me (or future-you) doesn't reopen this question without new information.
